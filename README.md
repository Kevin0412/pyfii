# Pyfii

## 简介
这个库的功能是可以让我们用 python 写 Fii 的无人机程序，以解决原软件无运算能力，无循环模块，一块块拖太烦等问题。

此外，这个库有三视图模拟飞行的功能，模拟飞行更方便观看。

## 安装
1. 使用 pip install 安装

    在命令行输入

        pip install pyfii

2. 下载源代码

    在命令行输入

        git clone https://github.com/Kevin0412/pyfii.git

    pyfii 就会被下载到当前目录下，使用时将 pyfii 文件夹复制到项目目录下

## pyfii 2.0 方向探索

pyfii 2.0 不一定要直接等同于 Web 化。更合理的目标是先把 **编队核心、轨迹采样、安全审查、渲染/预览** 解耦，让浏览器、桌面 3D 引擎、OpenCV 离线渲染都成为可替换的后端。

### 核心方向

- [ ] **pyfii-core**
  - 负责 `.fii` 读写、动作 DSL、轨迹采样、灯光时间轴、安全规则。
  - 尽量不依赖 GUI、OpenCV、Pygame、Web 框架。
  - 输出统一的轨迹 JSON/内存结构，供不同渲染后端消费。

- [ ] **pyfii-render**
  - 定义统一渲染接口，例如 `render(scene, timeline, camera, output)`。
  - 保留当前 OpenCV 渲染作为参考后端，用于回归对照。
  - 可并行试验多个现代 3D 方案，例如 pygfx/wgpu、Panda3D、VisPy、Godot viewer 或 Web/Three.js。

- [ ] **pyfii-app**
  - 面向实际使用的交互式预览工具。
  - 可以是浏览器应用，也可以是跨平台桌面应用。
  - Linux 开发优先，同时保证 Windows 可运行、可打包。

### 可视化路线候选

1. **桌面 3D 引擎路线**
   - 适合 Linux/Windows 本地开发和比赛调试。
   - 候选：pygfx/wgpu、Panda3D、VisPy。
   - 优点：Python 侧集成自然，不必先引入前后端服务。
   - 风险：不同显卡、驱动、打包环境需要实测。

2. **Web viewer 路线**
   - 后端解析 `.fii` 并提供轨迹数据，前端用 Canvas/Three.js 展示三视图和 3D。
   - 优点：交互体验、部署分享和跨平台一致性较好。
   - 风险：项目复杂度更高，PyPI 封装需要处理前端构建产物。

3. **保持 OpenCV 离线渲染路线**
   - 继续作为最低依赖的参考实现和自动化检查后端。
   - 适合批量生成视频、CI 检查和与 pyfii 1.x 视觉效果对齐。

### AI 编舞工作流探索

本次探索中，用 GPT 直接生成了一版 7 架 F400 编队程序，并通过 `output/gpt55_formation/review_keyframes.py` 做关键帧审查。阶段性结论是：**不必过度依赖完整视频理解闭环，强图像理解模型 + 关键帧/密采样审查也能有效推进编队质量。**

复杂编排可以参考 `tests/dntg20220730_v3.py` 的设计思路。需要注意：这个脚本的编码风格比较随意，不建议大规模模仿；它的价值不在于某一个具体图案或写法，而在于它展示了更成熟的编舞组织方式：

- **按音乐段落命名场景**：每一段都有清晰的 `startTime/endTime`，例如起飞、利萨如、斜对称、平移旋转、三维旋转、符号队形。
- **数学轨迹生成**：用复数、三角函数、利萨如曲线、旋转向量生成连续队形，而不是手写一堆静态坐标。
- **角色映射与重排**：通过 `[d4,d3,d2,d7,d1,d6,d5]`、`n2g1`、`n2g2`、`n2sg` 这类映射改变无人机职责，避免固定中心机或固定外圈。
- **分组并行动作**：同一时间层里，不同组执行不同逻辑，例如一组旋转、一组平移、一组做符号笔画。
- **运动与灯光交织**：每个移动段中穿插 100ms 级灯光渐变，让灯光成为节奏的一部分，而不是最后补上的装饰。
- **辅助函数表达意图**：例如用小函数表达“按时长移动”“自动高度”“生成一组目标点”，使复杂动作更易读。

后续 AI 生成不应照抄它的坐标或代码风格，而应学习这些结构：**场景分段 + 数学轨迹 + 角色轮换 + 分组关系 + 灯光节奏**。生成代码本身仍应保持清晰命名、函数化组织、少用隐式全局状态，并便于后续审查和修改。

需要特别澄清：**“扇区连续性”不是编舞风格，只是转场避撞的一种工程约束。** 它不能退化成“一架中心机不动，其他飞机围着转”的单调结构。更好的做法是把安全转场写成路径规划问题：

- 在相邻场景之间建立无人机到目标角色的分配关系，尽量减少交叉路径。
- 对容易交叉的角色交换，增加中间关键帧、错峰启动或分组通道，而不是强行保持环形队形。
- 可以使用多中心、双线、对角线、符号笔画、蛇形/波形、前后场交换等结构，只要转场路径经过审查。
- 高度层次可以增强画面，但不能作为唯一避撞手段；轨迹密采样仍应检查水平距离。
- AI 生成时要避免两个退化方向：一是“固定中心 + 外圈转”，二是“为了复杂而无规划地对穿换位”。

更进一步，AI 编舞不应该先从安全规则出发，而应该先从“动作设计”出发：

1. **先设计关键动作/关键队形**
   - 先按音乐段落写出几个真正想看的动作：例如开场亮相、利萨如/波形、斜对称、双组平移旋转、符号队形、收束。
   - 每个关键动作描述的是观感目标，而不是先被安全通道限制住。

2. **再设计衔接动作**
   - 在相邻关键动作之间补过渡：中间关键帧、错峰、分组通道、局部绕行、速度变化。
   - 衔接动作服务于“把上一个动作自然带到下一个动作”，而不是把整段表演压成固定安全模板。

3. **最后求解速度与时间**
   - 参考 `tests/function.py` 里的 `Time/Vel/move2` 思路：给定目标点和期望到达时间，反推出合适的 `VelXY/VelZ/Acc`，而不是全片使用固定速度。
   - 如果动作赶不上，就调整过渡时长、增加中间帧或改变目标分配；不要简单把安全距离写死后牺牲动作设计。
   - 速度调节本身也是编舞的一部分：慢动作、急促进入、错峰追随、高潮加速都应该能被表达。

新的工作流可以拆成：

1. **模型生成 pyfii 脚本**
   - 输入音乐信息、风格意图、机型/场地约束。
   - 输出完整可执行的 pyfii 程序。
   - 生成时可借鉴 `tests/dntg20220730_v3.py` 展示的复杂编排结构：命名段落、数学轨迹、分组映射、角色重排和灯光渐变；但不要模仿其随意的编码风格。
   - 推荐生成流程：先列关键动作，再生成衔接动作，最后用速度求解函数把每段移动落到 `VelXY/VelZ/move2/delay`。

2. **轨迹级自动检查**
   - 读取 `.fii` 后密采样轨迹。
   - 检查越界、最小水平距离、动作是否完成、时间轴是否单调。
   - 检查每架无人机的 XY 运动跨度，避免出现“固定中心机”或长期静止角色。
   - 检查转场路径是否存在中途对穿；安全不是要求永远保持环形顺序，而是要求每次角色交换都有可解释的中间路径。
   - 如果检查失败，优先修改衔接动作和速度/时间分配，而不是直接把艺术动作改成保守通道。
   - 这一层是硬安全门，优先于视觉评价。

3. **关键帧图像审查**
   - 在音乐段落点、强拍、转场点抽取俯视/三视图/3D 关键帧。
   - 用强图像理解模型评价队形层次、对称性、转场可读性、画面张力。
   - 重点检查视觉重心是否变化：中心、领舞、外圈、左右翼等角色是否轮换。
   - 如果画面长期围绕一架静止中心机运动，应退回重生成或局部修改。
   - 相比整段视频理解，关键帧更稳定、更便宜，也更容易定位问题。

4. **必要时再做视频理解**
   - 只在需要评价连续运动、节奏跟随、镜头观感时使用。
   - 不再把视频理解作为唯一或第一道反馈机制。

### GPT-5.5 成品种子已落入工作流

这次 60 秒 `burst_recompose` 成品动作已经不再只是一次性示例，而是沉淀为 `nl_choreo` 的关键帧种子：

- 固定时间轴与关键帧位于 `src/pyfii/extensions/nl_choreo/keyframe_workflow.py`。
- 可通过 `PipelineConfig(direct_fallback_mode="gpt55_burst_seed")` 接入现有工作流。
- 该模式会生成完整 pyfii 程序，继续经过 `.fii` 读回、距离检查和最终 2D/3D 预览渲染。
- 它不是新的安全限制模板，而是一条“成品动作种子”：当模型生成不稳定，或需要先有一版可运行视频时，用它打底；后续再让模型做局部优化。
- 种子现在带有四段动作设计元信息：斜线/钻石/冠形、双三角/丝带/箭形、反向弧/反击笔画、压缩/坠落/收束。报告会把这些段落写出来，便于后续人工或模型按段修改。
- 灯光只使用当前模拟器确定支持的控制方式：`TurnOnAll("#rrggbb")`、`TurnOffAll()` 和 `delay(100)`，不再依赖 per-LED 列表、呼吸、跑马等模拟器未稳定呈现的高级灯效。
- 动作不再是单一环形轨迹，而是由 `SCENES` 驱动 18 个三秒设计段落：宽斜线、钻石、桥接冠形、双三角、竖向断裂、丝带回弹、箭形锁定、外圈桥接、反向弧、反击丝带、宽斜切、压缩坠落和 bow 收束。速度按每段时长求解，移动期间用 100ms 直接灯光节拍填满。
- 动作逻辑保持“相邻关系 + 环形桥接 + 角色循环移位”的轻约束表达，用连续轨迹和读回安全检查兜底；它不会把飞机锁进固定安全区域，也不强制固定中心机。
- 工作流现在把“不要退化成固定车道”沉淀成了动态指标：`evaluate_timeline_dynamics()` 会统计相邻关键层的角色排序变化、每架机 XY 跨度等；`validate_timeline_dynamics()` 会拒绝排序长期不变、单轴跨度过小的候选动作。当前 GPT-5.5 seed 的 19 次相邻转场中有 18 次发生角色排序变化，平均 rank change 约 11.16；每架机的 X/Y 跨度都超过 320cm。后续候选至少不能低于这个基线，否则即使安全可跑，也应视作固定车道退化。

cfg = PipelineConfig(

### 与 `dntg20220730_v3.py` 的差距反思

当前 GPT-5.5 种子已经完成了“可运行、可读回、可渲染”的闭环，也避免了固定中心机绕圈 50 秒的错误退化。但它距离 `tests/dntg20220730_v3.py` 这种成熟手写编舞仍然有明显差距：现在的种子本质上还是 18 个三秒关键队形的串联，移动期间再用 100ms 直接灯光节拍填满；而 `dntg20220730_v3.py` 更像一份动作乐谱，每个段落内部都有自己的动作语法。

关键差距不在于队形数量，而在于段内逻辑：

- `dntg20220730_v3.py` 的起飞段不是一次到位，而是三次扩张并配合渐亮；利萨如段有 `li/li1/li2/li3` 轨迹表、角色步进和通道重排。
- 它会按段建立临时角色映射，例如 `n2g1`、`n2g2`、`n2gn`、`n2sg`，让中心、外圈、边缘、符号点等角色随段落变化，而不是由全局关键帧隐式决定。
- 它经常使用等待、半拍错位和分组差异：有的飞机先绕开，有的飞机停半拍，有的组旋转，有的组平移，形成节奏上的缓急。
- 它的灯光不是附着在关键帧上的颜色标签，而是跟动作小节同步的 100ms 或 600ms 节拍；即使只用 `TurnOnAll/TurnOffAll`，也能表达渐变、闪断、分段换色和段落高潮。
- 它使用数学结构表达动作意图，例如复数旋转、Lissajous-like 点表、环形向量、高度相位和符号点缩放；这些结构比单纯列出目标点更容易产生“设计感”。

因此，下一版工作流不应继续把目标定义为“生成更多关键帧”。正确方向是让模型先生成可解释的段落动作程序：

- 每段输出 `scene_id`、起止时间、分组、角色映射、局部轨迹函数、段内 step 时长和灯光节拍。
- 关键帧图像只作为审查与回写依据，而不是动作生成的唯一表达。
- 安全检查应作用在段内小步和读回轨迹上；失败时优先修正衔接、等待、速度和角色映射，而不是把动作收缩成保守固定区域。
- “相邻保持 + 环形桥接 + 角色循环移位”应作为软设计原则进入段落生成，而不是变成全局安全笼子。

换句话说，现在的 GPT-5.5 种子只是一个可靠骨架；要接近 `dntg20220730_v3.py`，工作流需要从 pose-driven 关键帧生成，升级为 action-score-driven 段落编舞生成。

### 阶段结论

- 2.0 的重点应从“换一个显示方式”转向“建立可插拔的编队模拟与审查架构”。
- 浏览器化仍然值得保留为方向之一，但不必成为唯一主线。
- 强模型生成编队脚本已经可行，后续关键在于建立稳定的自动审查指标和可视化反馈。
- 关键帧审查是一个很实用的折中点：它比纯代码检查更接近观感，又比完整视频理解更可控。
- AI 编舞提示词需要明确“角色轮换”与“每架机都有 XY 运动跨度”，否则模型容易退化成固定中心机 + 外圈旋转的单一套路。
- 下一步建议优先做 `pyfii-core` 的轨迹 JSON 契约，再并行试验桌面 3D 后端和 Web viewer。
