# Pyfii

## 简介
这个库的功能是可以让我们用 python 写 Fii 的无人机程序，以解决原软件无运算能力，无循环模块，一块块拖太烦等问题。

此外，这个库有三视图模拟飞行的功能，模拟飞行更方便观看。

## 安装
1. 使用 pip install 安装

    在命令行输入

        pip install pyfii

2. 下载源代码

    在命令行输入

        git clone https://github.com/Kevin0412/pyfii.git

    pyfii 就会被下载到当前目录下，使用时将 pyfii 文件夹复制到项目目录下

## pyfii 2.0 方向探索

pyfii 2.0 不一定要直接等同于 Web 化。更合理的目标是先把 **编队核心、轨迹采样、安全审查、渲染/预览** 解耦，让浏览器、桌面 3D 引擎、OpenCV 离线渲染都成为可替换的后端。

### 核心方向

- [ ] **pyfii-core**
  - 负责 `.fii` 读写、动作 DSL、轨迹采样、灯光时间轴、安全规则。
  - 尽量不依赖 GUI、OpenCV、Pygame、Web 框架。
  - 输出统一的轨迹 JSON/内存结构，供不同渲染后端消费。

- [ ] **pyfii-render**
  - 定义统一渲染接口，例如 `render(scene, timeline, camera, output)`。
  - 保留当前 OpenCV 渲染作为参考后端，用于回归对照。
  - 可并行试验多个现代 3D 方案，例如 pygfx/wgpu、Panda3D、VisPy、Godot viewer 或 Web/Three.js。

- [ ] **pyfii-app**
  - 面向实际使用的交互式预览工具。
  - 可以是浏览器应用，也可以是跨平台桌面应用。
  - Linux 开发优先，同时保证 Windows 可运行、可打包。

### 可视化路线候选

1. **桌面 3D 引擎路线**
   - 适合 Linux/Windows 本地开发和比赛调试。
   - 候选：pygfx/wgpu、Panda3D、VisPy。
   - 优点：Python 侧集成自然，不必先引入前后端服务。
   - 风险：不同显卡、驱动、打包环境需要实测。

2. **Web viewer 路线**
   - 后端解析 `.fii` 并提供轨迹数据，前端用 Canvas/Three.js 展示三视图和 3D。
   - 优点：交互体验、部署分享和跨平台一致性较好。
   - 风险：项目复杂度更高，PyPI 封装需要处理前端构建产物。

3. **保持 OpenCV 离线渲染路线**
   - 继续作为最低依赖的参考实现和自动化检查后端。
   - 适合批量生成视频、CI 检查和与 pyfii 1.x 视觉效果对齐。

### AI 编舞工作流探索

> 归档说明：`nl_choreo` / Qwen 视频理解闭环已从主线移入 `archive/nl_choreo_qwen/`。这条路的核心误判是把“视频理解”当成连续动作理解；实际模型仍然主要依赖抽帧，2fps 对无人机编队的速度、错峰、路径交叉和节奏损失太大。后续主线转向强模型直接设计 motion brief / phrase spec / pyfii 脚本，再由本地读回、密采样、安全检查和 2D/3D 视频验收。

本次探索中，用 GPT 直接生成了一版 7 架 F400 编队程序，并通过 `output/gpt55_formation/review_keyframes.py` 做关键帧审查。阶段性结论是：**不必过度依赖完整视频理解闭环，强图像理解模型 + 关键帧/密采样审查也能有效推进编队质量。**

复杂编排可以参考 `tests/dntg20220730_v3.py` 的设计思路。需要注意：这个脚本的编码风格比较随意，不建议大规模模仿；它的价值不在于某一个具体图案或写法，而在于它展示了更成熟的编舞组织方式：

- **按音乐段落命名场景**：每一段都有清晰的 `startTime/endTime`，例如起飞、利萨如、斜对称、平移旋转、三维旋转、符号队形。
- **数学轨迹生成**：用复数、三角函数、利萨如曲线、旋转向量生成连续队形，而不是手写一堆静态坐标。
- **角色映射与重排**：通过 `[d4,d3,d2,d7,d1,d6,d5]`、`n2g1`、`n2g2`、`n2sg` 这类映射改变无人机职责，避免固定中心机或固定外圈。
- **分组并行动作**：同一时间层里，不同组执行不同逻辑，例如一组旋转、一组平移、一组做符号笔画。
- **运动与灯光交织**：每个移动段中穿插 100ms 级灯光渐变，让灯光成为节奏的一部分，而不是最后补上的装饰。
- **辅助函数表达意图**：例如用小函数表达“按时长移动”“自动高度”“生成一组目标点”，使复杂动作更易读。

后续 AI 生成不应照抄它的坐标或代码风格，而应学习这些结构：**场景分段 + 数学轨迹 + 角色轮换 + 分组关系 + 灯光节奏**。生成代码本身仍应保持清晰命名、函数化组织、少用隐式全局状态，并便于后续审查和修改。

需要特别澄清：**“扇区连续性”不是编舞风格，只是转场避撞的一种工程约束。** 它不能退化成“一架中心机不动，其他飞机围着转”的单调结构。更好的做法是把安全转场写成路径规划问题：

- 在相邻场景之间建立无人机到目标角色的分配关系，尽量减少交叉路径。
- 对容易交叉的角色交换，增加中间关键帧、错峰启动或分组通道，而不是强行保持环形队形。
- 可以使用多中心、双线、对角线、符号笔画、蛇形/波形、前后场交换等结构，只要转场路径经过审查。
- 高度层次可以增强画面，但不能作为唯一避撞手段；轨迹密采样仍应检查水平距离。
- AI 生成时要避免两个退化方向：一是“固定中心 + 外圈转”，二是“为了复杂而无规划地对穿换位”。

更进一步，AI 编舞不应该先从安全规则出发，而应该先从“动作设计”出发：

1. **先设计关键动作/关键队形**
   - 先按音乐段落写出几个真正想看的动作：例如开场亮相、利萨如/波形、斜对称、双组平移旋转、符号队形、收束。
   - 每个关键动作描述的是观感目标，而不是先被安全通道限制住。

2. **再设计衔接动作**
   - 在相邻关键动作之间补过渡：中间关键帧、错峰、分组通道、局部绕行、速度变化。
   - 衔接动作服务于“把上一个动作自然带到下一个动作”，而不是把整段表演压成固定安全模板。

3. **最后求解速度与时间**
   - 参考 `tests/function.py` 里的 `Time/Vel/move2` 思路：给定目标点和期望到达时间，反推出合适的 `VelXY/VelZ/Acc`，而不是全片使用固定速度。
   - 如果动作赶不上，就调整过渡时长、增加中间帧或改变目标分配；不要简单把安全距离写死后牺牲动作设计。
   - 速度调节本身也是编舞的一部分：慢动作、急促进入、错峰追随、高潮加速都应该能被表达。

新的工作流可以拆成：

1. **模型生成 pyfii 脚本**
   - 输入音乐信息、风格意图、机型/场地约束。
   - 输出完整可执行的 pyfii 程序。
   - 生成时可借鉴 `tests/dntg20220730_v3.py` 展示的复杂编排结构：命名段落、数学轨迹、分组映射、角色重排和灯光渐变；但不要模仿其随意的编码风格。
   - 推荐生成流程：先列关键动作，再生成衔接动作，最后用速度求解函数把每段移动落到 `VelXY/VelZ/move2/delay`。

2. **轨迹级自动检查**
   - 读取 `.fii` 后密采样轨迹。
   - 检查越界、最小水平距离、动作是否完成、时间轴是否单调。
   - 检查每架无人机的 XY 运动跨度，避免出现“固定中心机”或长期静止角色。
   - 检查转场路径是否存在中途对穿；安全不是要求永远保持环形顺序，而是要求每次角色交换都有可解释的中间路径。
   - 如果检查失败，优先修改衔接动作和速度/时间分配，而不是直接把艺术动作改成保守通道。
   - 这一层是硬安全门，优先于视觉评价。

3. **关键帧图像审查**
   - 在音乐段落点、强拍、转场点抽取俯视/三视图/3D 关键帧。
   - 用强图像理解模型评价队形层次、对称性、转场可读性、画面张力。
   - 重点检查视觉重心是否变化：中心、领舞、外圈、左右翼等角色是否轮换。
   - 如果画面长期围绕一架静止中心机运动，应退回重生成或局部修改。
   - 相比整段视频理解，关键帧更稳定、更便宜，也更容易定位问题。

4. **必要时再做视频理解**
   - 只在需要评价连续运动、节奏跟随、镜头观感时使用。
   - 不再把视频理解作为唯一或第一道反馈机制。

### 归档记录：GPT-5.5/nl_choreo 种子

以下内容保留为归档记录，不再代表主线工作流。相关代码已移动到 `archive/nl_choreo_qwen/`：

- 固定时间轴与关键帧位于 `archive/nl_choreo_qwen/src/pyfii/extensions/nl_choreo/keyframe_workflow.py`。
- 原 `PipelineConfig(direct_fallback_mode="gpt55_burst_seed")` 路线已归档。
- 该模式会生成完整 pyfii 程序，继续经过 `.fii` 读回、距离检查和最终 2D/3D 预览渲染。
- 它不是新的安全限制模板，而是一条“成品动作种子”：当模型生成不稳定，或需要先有一版可运行视频时，用它打底；后续再让模型做局部优化。
- 种子现在带有四段动作设计元信息：斜线/钻石/冠形、双三角/丝带/箭形、反向弧/反击笔画、压缩/坠落/收束。报告会把这些段落写出来，便于后续人工或模型按段修改。
- 灯光只使用当前模拟器确定支持的控制方式：`TurnOnAll("#rrggbb")`、`TurnOffAll()` 和 `delay(100)`，不再依赖 per-LED 列表、呼吸、跑马等模拟器未稳定呈现的高级灯效。
- 动作不再是单一环形轨迹，而是由 `SCENES` 驱动 18 个三秒设计段落：宽斜线、钻石、桥接冠形、双三角、竖向断裂、丝带回弹、箭形锁定、外圈桥接、反向弧、反击丝带、宽斜切、压缩坠落和 bow 收束。速度按每段时长求解，移动期间用 100ms 直接灯光节拍填满。
- 动作逻辑保持“相邻关系 + 环形桥接 + 角色循环移位”的轻约束表达，用连续轨迹和读回安全检查兜底；它不会把飞机锁进固定安全区域，也不强制固定中心机。
- 工作流现在把“不要退化成固定车道”沉淀成了动态指标：`evaluate_timeline_dynamics()` 会统计相邻关键层的角色排序变化、每架机 XY 跨度等；`validate_timeline_dynamics()` 会拒绝排序长期不变、单轴跨度过小的候选动作。当前 GPT-5.5 seed 的 19 次相邻转场中有 18 次发生角色排序变化，平均 rank change 约 11.16；每架机的 X/Y 跨度都超过 320cm。后续候选至少不能低于这个基线，否则即使安全可跑，也应视作固定车道退化。

归档 demo 位于 `archive/nl_choreo_qwen/examples/nl_choreo_gpt55_seed_demo.py`。

### 与 `dntg20220730_v3.py` 的差距反思

当前 GPT-5.5 种子已经完成了“可运行、可读回、可渲染”的闭环，也避免了固定中心机绕圈 50 秒的错误退化。但它距离 `tests/dntg20220730_v3.py` 这种成熟手写编舞仍然有明显差距：现在的种子本质上还是 18 个三秒关键队形的串联，移动期间再用 100ms 直接灯光节拍填满；而 `dntg20220730_v3.py` 更像一份动作乐谱，每个段落内部都有自己的动作语法。

关键差距不在于队形数量，而在于段内逻辑：

- `dntg20220730_v3.py` 的起飞段不是一次到位，而是三次扩张并配合渐亮；利萨如段有 `li/li1/li2/li3` 轨迹表、角色步进和通道重排。
- 它会按段建立临时角色映射，例如 `n2g1`、`n2g2`、`n2gn`、`n2sg`，让中心、外圈、边缘、符号点等角色随段落变化，而不是由全局关键帧隐式决定。
- 它经常使用等待、半拍错位和分组差异：有的飞机先绕开，有的飞机停半拍，有的组旋转，有的组平移，形成节奏上的缓急。
- 它的灯光不是附着在关键帧上的颜色标签，而是跟动作小节同步的 100ms 或 600ms 节拍；即使只用 `TurnOnAll/TurnOffAll`，也能表达渐变、闪断、分段换色和段落高潮。
- 它使用数学结构表达动作意图，例如复数旋转、Lissajous-like 点表、环形向量、高度相位和符号点缩放；这些结构比单纯列出目标点更容易产生“设计感”。

因此，下一版工作流不应继续把目标定义为“生成更多关键帧”。正确方向是让模型先生成可解释的段落动作程序：

- 每段输出 `scene_id`、起止时间、分组、角色映射、局部轨迹函数、段内 step 时长和灯光节拍。
- 关键帧图像只作为审查与回写依据，而不是动作生成的唯一表达。
- 安全检查应作用在段内小步和读回轨迹上；失败时优先修正衔接、等待、速度和角色映射，而不是把动作收缩成保守固定区域。
- “相邻保持 + 环形桥接 + 角色循环移位”应作为软设计原则进入段落生成，而不是变成全局安全笼子。

换句话说，现在的 GPT-5.5 种子只是一个可靠骨架；要接近 `dntg20220730_v3.py`，工作流需要从 pose-driven 关键帧生成，升级为 action-score-driven 段落编舞生成。

### 后续：从固定模板走向 phrase-based 设计

`archive/nl_choreo_qwen/examples/gpt55_action_score_v2_60s.py` 和 `archive/nl_choreo_qwen/examples/gpt55_template_motion_v2_60s.py` 证明了一个方向：在 GPT-5.5 seed 的主关键帧之间加入动作小节、曲线中间态、垂直起伏和角色重排，比单纯关键帧直连更接近真正的编舞。但它们仍然只是过渡形态：

- `action_score_v2` 仍然主要按场景名推导段内曲线，属于半模板化增强。
- `template_motion_v2` 把段内动作显式拆成 `bloom_pulse`、`braid_recoil`、`orbit_sling`、`vertical_shutter`、`compression_ring` 等模板，更容易复用和调参，但本质仍是固定模板库。
- 固定动作模板不能成为最终答案。模板可以作为动作原语、调试基线和失败回退，但不应该限制每次生成只能在几套既有动作之间排列组合。
- “每 3 秒一个段落、每段一个模板、模板均匀排布”本身也是枷锁。即使模板本身是好的，均匀铺开也会让整段表演缺少长句、停顿、追赶、爆发和回收。

下一阶段更合理的目标是 **phrase-based choreography**：让模型每次根据音乐、风格和用户反馈重新设计动作短句/长句，而不是只选择模板。一个动作 phrase 应该能表达：

- 非均匀时间：有的动作 1.2 秒快速切入，有的动作 4-5 秒慢慢展开，不再固定三秒一格。
- 跨段动作：一个弧扫、压缩、追逐或回弹可以横跨多个关键造型，而不是被场景边界切碎。
- 分组分工：同一时刻可以让 3 架机做外环、2 架机做穿插、2 架机做高度反拍，而不是全队套同一个模板。
- 动作原语组合：把弧扫、径向收缩、高度错层、角色交换、延迟释放、错峰追随等作为可组合原语，由模型临场组成新的动作语言。
- 情绪曲线：前段建立空间，中段增加穿插，高潮前压缩或停顿，高潮段连续释放，尾段收束；时间密度应服务于观感，而不是服务于模板表。

工作流上，应逐步变成多轮对话式的 “vibe coding” 编舞：

1. 用户用自然语言给出方向，例如“30-45 秒更狠一点，别太平面，最后别排成一条线”。
2. 模型先生成或修改 motion spec，而不是直接堆坐标。motion spec 应记录 `time range`、`drone groups`、`intent`、`motion primitives`、`role mapping`、`timing notes`、`risk` 和 `repair strategy`。
3. 代码生成器把 motion spec 转成 pyfii 动作：自动求解速度/加速度，插入中间点、等待、错峰和分组轨迹。
4. 读回 `.fii` 后用硬指标检查最小距离、动作是否完成、越界、XY/Z 跨度、角色排序变化、固定车道退化和中途对穿风险。
5. 渲染关键帧/视频后，把视觉反馈回写到 motion spec；用户继续用自然语言改，模型只改对应 phrase，而不是整段推倒重来。

因此，模板库的长期定位应是 **动作词汇表**，不是成片编排表。真正的目标是每次都能生成一套新的动作设计，并在多轮反馈中局部重写、收紧、放大或改节奏，同时保留安全读回和可复现输出。

### 本轮 v4-v9 收尾结论

本轮从 v4 到 v9 的试验暴露了几个明确边界：

- `random`/候选搜索不能替代动作设计。它可以用于离线探索可能的点位，但最终进入工作流的脚本必须是可解释、可复现的命名动作短句。
- 单个 `rotation` 或 ribbon 场很容易把视觉退化成整体逆/顺时针旋转。局部旋转可以保留，但全片必须混入反向切割、错层穿插、压缩爆开、分组换位和非环形结构。
- 安全硬门只认 PyFii 本身的危险信号：`distance between` 和 `action isn't completed`。最小距离可以作为报告指标，但不应私自加“保守阈值”替代 PyFii 判断。
- 速度慢不是安全本身。正确做法是给每段动作按距离和时长求解 `VelXY/VelZ/Acc`，飞不完就修衔接、分段或目标分配，而不是把整段降速。
- 视频是最终验收物。代码、指标和关键帧只能辅助判断；每次声称动作优化，都必须产出可观看的 2D/3D 视频。

当前手写验证版归档为 `archive/nl_choreo_qwen/examples/original_crosscut_v9_60s.py`，输出：

- `output/original_crosscut_v9_60s/original_crosscut_v9_60s.mp4`
- `output/original_crosscut_v9_60s/render_crosscut_v9_3d.mp4`

这版 v9 的定位不是最终模板，而是新的基线：**手写 phrase + 确定性换位 + PyFii 读回硬门 + 3D 视频验收**。它证明了“不靠 random、不靠固定模板、不靠全局旋转”这条路可行。

工作流因此更新为：

1. **先写 motion brief**
   - 用自然语言列出段落意图，例如“交叉切入、错层换位、压缩爆开、反向斜切”。
   - 明确哪些段落是快切、哪些是长句、哪些是停顿/释放，不再默认均匀 3 秒格。

2. **再写 phrase/action-score**
   - 每段包含 `time range`、`intent`、`groups`、`role mapping`、`motion primitives`、`risk`、`repair strategy`。
   - `random`、`random_search`、`global_rotation`、`single_center_orbit`、`fixed_lane`、`uniform_template_grid` 这类原语禁止作为最终设计。

3. **再生成 pyfii 程序**
   - 目标点和轨迹来自 phrase 设计。
   - 程序可以使用确定性分配、速度求解、中间关键帧和错峰来保证可执行性。
   - 搜索/优化只能服务于“如何安全到达已设计动作”，不能反过来决定动作本身。

4. **硬检查**
   - `pf.Fii(...).save()`、`pf.read_fii(...)`、`pf.show(...)` 的 warning 都要捕获。
   - 出现 `distance between` 或 `action isn't completed` 直接失败。
   - 同时报告 readback 最小距离、最大单段位移、平均位移、最长停顿、角色转向分布等指标。

5. **视频验收**
   - 必须输出完整 2D/3D 视频。
   - 看视频判断是否退化成固定车道、整体旋转、模板串联、速度过慢或动作不连贯。

### 纯文本模型是否可行

纯文本模型可行，但前提是把“视觉理解”从生成环节拆出去。也就是说：文本模型负责 **设计 motion brief / phrase spec / pyfii 代码**，PyFii 和本地脚本负责 **读回、采样、碰撞、速度、跨度、退化指标、渲染视频**。

它适合做的事：

- 生成分段动作意图、角色映射、分组关系、节奏说明和修复策略。
- 根据用户反馈局部改 phrase，例如“30-45 秒更狠”“别全逆时针”“中段加快”“最后不要排直线”。
- 生成可执行 pyfii 程序，并在失败报告后修代码。
- 对指标报告做归因：哪里飞不完、哪里太慢、哪里像模板、哪里疑似固定车道。

它不适合单独做的事：

- 直接判断视频好不好看。
- 仅凭文字保证没有中途对穿。
- 仅凭坐标列表判断最终观感节奏。

因此 DeepSeek-v4、GPT、Claude 等纯文本/弱视觉模型可以这样测：

1. **同题输入**
   - 同一个 60 秒任务、同一机型 F400、同一场地、同一硬约束。
   - 输入包含当前 README 的工作流摘要、PyFii 用法、禁止项和 v9 基线说明。

2. **两阶段输出**
   - 第一轮只输出 motion brief/phrase spec，不写代码。
   - 第二轮根据 phrase spec 输出完整 pyfii 脚本。

3. **统一本地验收**
   - 运行脚本生成 `.fii` 和视频。
   - 捕获 PyFii warning。
   - 记录 readback 最小距离、动作完成、时长、单段位移、停顿、XY 跨度、角色轮换、全局旋转倾向。
   - 输出 2D/3D 视频给人看。

4. **评分**
   - 硬失败：PyFii 报距离或动作未完成、脚本不可运行、无完整视频。
   - 软失败：固定中心/固定车道、全局单向旋转、模板均匀串联、速度明显慢、动作不连贯。
   - 通过：有明确原创动作句法、可读回、视频可看、能按反馈局部修改。

如果要测 DeepSeek-v4，不要先假设视觉能力；把它当作 OpenAI-compatible 文本模型接入即可。根目录 `ai_providers.example.json` 保留了 `custom_gpt`、`deepseek`、`deepseek_pro` 三条 provider 配置样例；视频理解闭环已经归档，后续只把视频作为人工或独立验收物。

示例 provider 配置：

```json
{
  "provider": "custom_gpt",
  "providers": {
    "custom_gpt": {
      "base_url": "",
      "api_key": "",
      "model": "gpt-5.5",
      "reasoning_effort": "xhigh",
      "max_output_tokens": 98304
    },
    "deepseek_pro": {
      "base_url": "https://api.deepseek.com",
      "api_key": "",
      "model": "deepseek-v4-pro",
      "reasoning_effort": "max",
      "extra_body": {
        "thinking": {
          "type": "enabled"
        }
      }
    }
  }
}
```

后续强模型路径应先测“模型能否产出 motion brief / phrase spec / 可运行脚本”，再由本地读回、密采样和视频渲染验收，不再让模型硬吃完整视频闭环。

### 阶段结论

- 2.0 的重点应从“换一个显示方式”转向“建立可插拔的编队模拟与审查架构”。
- 浏览器化仍然值得保留为方向之一，但不必成为唯一主线。
- 强模型生成编队脚本已经可行，但最终目标不是“套模板生成”，而是“文本设计 phrase、本地验证轨迹、视频验收结果”。
- 关键帧审查是一个很实用的折中点：它比纯代码检查更接近观感，又比完整视频理解更可控。
- AI 编舞提示词需要明确“角色轮换”与“每架机都有 XY 运动跨度”，否则模型容易退化成固定中心机 + 外圈旋转的单一套路。
- 纯文本模型值得测，尤其适合 motion brief、phrase spec、代码生成和失败修复；视觉评价则交给 PyFii 渲染视频 + 人工/视觉模型复核。
- 下一步建议优先做 `pyfii-core` 的轨迹 JSON 契约，再并行试验桌面 3D 后端和 Web viewer。
